# 아키텍처

시스템별 구조와 **왜 그렇게 했는지**. 구현 현황은 [STATUS.md](STATUS.md)를 보세요.

> **이 문서는 지금 코드를 설명합니다.** 2026-10-25에 메카로 기획이 바뀌었고([PIVOT.md](PIVOT.md)) 아래 절 중 일부는 전환 대상입니다. 각 절 머리에 ⚠ 로 표시해 두었습니다. 전환 후 구조는 PIVOT에 있고, 구현되는 대로 이쪽으로 옮깁니다.

## Agent 컴포지션

전투 주체는 `Agent`이고, 기능은 상속이 아니라 **컴포넌트**로 붙입니다.

```csharp
public class Health : MonoBehaviour, IAgentComponent
```

`Agent.Awake`가 자식의 `IAgentComponent`를 전부 모아 `Initialize(Agent)` → `AfterInitialize()` 순으로 부르고, `OnDestroy`에서 `Dispose()`를 전파합니다.

**컴포넌트끼리 참조가 필요하면 `AfterInitialize`에서** `owner.GetCompo<T>()`로 잡습니다. `Initialize` 시점엔 아직 다 모이지 않았을 수 있습니다.

`Agent` 없이도 동작해야 하는 컴포넌트(폭발통, 파괴 가능한 엄폐물)는 `Awake`에서 부모에 `Agent`가 없을 때만 스스로 초기화합니다. `Health`, `TargetBase`가 이 패턴입니다.

## 타게팅과 전투 판정

책임이 네 갈래입니다. 섞지 마세요.

| | 담당 |
|---|---|
| `TargetBase` | **맞기 전.** 타게팅 단위(동일성 기준), 분류, 레이어 동기화, 소실 알림, 조준점 |
| `Health` / `IDamageable` | **맞은 뒤.** HP, 피해 계산, 사망 |
| `HitBox` | 콜라이더 → 소속 대상 직접 참조 + 부위 배율 |
| `CasterBase` | 대상 탐색, 필터링, **중복 제거**, 이펙터 분배 |

### 왜 TargetBase가 따로 있나

한 유닛이 히트박스를 여러 개 갖게 되면 `OverlapCircle`이 같은 적의 머리·몸통·다리를 한 번에 돌려줍니다. 이걸 접어주는 **동일성 기준**이 필요하고, 그게 `TargetBase`입니다. 폭발 한 방에 데미지가 세 번 들어가는 걸 막습니다.

`CasterBase.Cast()`가 콜라이더 목록을 `CastHit` 목록으로 접고, 생존 확인·자기 자신 제외도 여기서 끝냅니다. `ICastEffector` 구현체는 그런 검사를 다시 하지 않습니다.

### TargetType과 레이어

`TargetType`은 `[Flags]`입니다. 유닛은 하나만, 캐스터는 조합해서 씁니다.

물리 레이어 대응은 `TargetLayerTableSO`(`Resources/TargetLayerTable.asset`) 한 곳에만 있습니다. **캐스터가 LayerMask를 직접 들고 있으면 안 됩니다** — "이 캐스터의 TargetType"과 "이 캐스터의 LayerMask"가 따로 놀아서 어긋납니다.

지상↔공중 전환 시 물리 캐스터는 매번 새로 질의하므로 자동으로 맞습니다. 참조를 캐시한 쪽(유도탄, AI 어그로, 락온 UI)만 `OnTargetTypeChangedEvent` / `OnTargetLostEvent`를 구독해 다시 판단하면 됩니다.

## 스탯

`Status<T>`는 기본값 + modifier 목록이고 dirty 캐싱합니다.

**modifier는 origin 객체를 키로** 걸고 뗍니다. 버프를 건 주체가 사라질 때 `RemoveModifier(origin)`으로 정확히 그것만 걷어낼 수 있어야 합니다. origin은 참조 동일성으로 비교하므로 **박싱된 enum 같은 값 타입을 쓰면 안 됩니다.**

계산식:

```
(기본값 + 덧셈 전부) * (1 + 비율 전부)
```

덧셈을 다 적용한 뒤 비율을 곱하므로 **적용 순서가 결과를 바꾸지 않습니다.** 모듈 끼운 순서에 따라 최종 수치가 달라지면 재현 안 되는 밸런싱 버그가 됩니다.

타입별 합산 규칙은 `StatusCombiner`에 있습니다 (float/int 합산, bool OR). 닫힌 제네릭 타입마다 델리게이트를 한 번만 해석해서 박싱이 없습니다.

## 데미지

```
방어력은 깡 차감, 저항은 % 감소
final = max(damage - defense, floor) * (1 - clamp01(resistance))
```

`floor`는 `min(damage, MinDamage)`입니다. 방어력이 아무리 높아도 최소 피해는 들어가되, 원래 데미지가 그보다 작으면 깡 차감이 오히려 데미지를 늘리는 일은 없습니다.

치명타는 `DamageHandler.CalculateDamage`에서 굴립니다. `criticalRate`가 1을 넘으면 치명타 확정 + 초과분이 극대화 확률.

`AgentStatus.IsResist`(bool)는 **상태이상 면역**이고, 피해 감소는 `DamageResistance`(float)입니다. 이름이 비슷하니 헷갈리지 마세요.

## 상태이상

`ConditionType` enum + `ConditionFactory`로 생성하고, 강도는 **타입별 상수 × Level**입니다.

같은 타입이 재적용되면 지속시간은 갱신하고, **레벨이 더 높으면** `OnEnd()` → 레벨 교체 → `OnStart()`로 다시 겁니다. modifier 계열(Weakness 등)이 중첩되지 않게 하기 위해서입니다.

구현 형태가 세 가지입니다 — 도트(`DamageOverTimeCondition`), 스탯 modifier(`WeaknessCondition`), 플래그만(`StunCondition`).

## 오브젝트 풀

`PoolListSO`가 전체 카탈로그, `PoolPresetSO`가 씬/세션별로 미리 만들 것입니다. `PoolManager`는 프리셋을 여러 개 받으므로 `Common + Stage1` 식으로 조합합니다.

`PoolItem.Id`가 생성된 `PoolType` enum 값과 1:1이고 재사용되지 않으므로, 이름을 바꾸거나 순서를 바꿔도 저장된 참조가 안 깨집니다. `PoolManager`는 시작할 때 `(PoolType)Id`가 실제 enum에 있는지 이름까지 대조합니다.

**`PoolType.cs`는 자동 생성 파일입니다.** 직접 고치지 말고 `Tools > Pool Manager`의 Generate Enum을 쓰세요.

`IPoolable`만으로는 `SelfObject`를 구현할 수 없어(인터페이스에 필드가 없음) `PoolableMono` 추상 클래스가 짝으로 있습니다. 풀 대상은 `PoolableMono`를 상속하세요.

## 아이템 데이터

모든 게임 데이터(무기·모듈·블럭·자원·유닛)는 `ItemDataSO` 파생입니다. **식별은 `uint Id` 하나로만** 합니다.

`ItemDatabaseSO`가 유일한 레지스트리이고, 인스펙터의 "프로젝트 스캔 & 갱신"이 Id를 부여합니다. **한 번 부여된 Id는 절대 바뀌지 않고 재사용되지 않습니다.**

### Id 대역

Id를 만든 순서대로 1, 2, 3으로 주면 **번호만 보고는 그게 무엇인지 알 수 없습니다.** 로그·세이브 파일·네트워크 패킷에서 종류가 바로 읽히도록 타입별로 번호대를 나눕니다.

```
    1 ~   999   기타 / 미분류   ItemDataSO      ← 대역을 못 찾은 것이 여기로 떨어진다
 1000 ~  1999   무기            PlayerWeaponDataSO
 2000 ~  2999   모듈            ModuleDataSO
 3000 ~  3999   탄약            AmmoDataSO
 4000 ~  9999   도구·기체 파츠·자원·블럭·유닛 (예약)
```

> ⚠ **기체 파츠(코어·추진체) 대역을 예약 구간에서 새로 떼야 합니다.** 무기는 1000 대역을 그대로 쓰고(팔 슬롯에 들어가는 것이 곧 무기입니다), 코어·추진체만 새 대역이 필요합니다.

표는 `ItemDatabaseSO._idRanges`에 있고 인스펙터에서 편집합니다. 예약 대역은 `typeName`을 비워둔 자리이고, 클래스를 만들면 이름만 채우면 됩니다.

**키는 SO 파생 타입입니다.** `ItemCategoryType`이 아닙니다 — 표시 전용이라 언제든 바뀌는데 Id는 바뀌지 않으므로, 그걸로 나누면 대역 밖에 남는 아이템이 생깁니다.

타입에 대역이 없으면 **부모로 거슬러 올라갑니다.** `ShotgunDataSO : PlayerWeaponDataSO`를 새로 만들어도 설정 없이 무기 대역을 물려받습니다. `ItemDataSO` 자신이 표에 있으므로 결국 어딘가에서는 잡힙니다.

**커서는 대역마다 따로입니다.** 하나의 전역 `_nextId`로는 무기를 지웠을 때 그 번호가 탄약에게 넘어갑니다. 대역이 꽉 차면 옆으로 넘기지 않고 Id를 주지 않은 채 에러를 냅니다 — 조용히 넘기면 대역을 나눈 의미가 사라집니다.

`_nextId`는 대역이 없는 타입을 위한 예비 커서로만 남아 있습니다.

아이템 전체를 아우르는 enum은 **만들지 않습니다.** 도감처럼 "전체 목록"이 필요한 기능은 `database.All`을 순회하세요. 아이템이 몇백 개로 늘어도 코드는 그대로고, enum 재생성에 따른 리컴파일도 없습니다.

`ItemCategoryType`은 **표시 목적 전용**입니다(정렬·필터). 장착 가능 여부 같은 사용처 판정은 `PlayerWeaponDataSO` 같은 **파생 타입**으로 하세요.

### 이름은 세 겹이다

한 아이템이 이름을 세 개 갖습니다. 역할이 달라서 합칠 수 없습니다.

| | 필드 | 쓰임 | 화면에 나오나 |
|---|---|---|---|
| 에디터 식별자 | `_editorName` | 에셋 이름 규칙(`Item_Ammo_RustySmall`)의 재료 | ✗ |
| 기본 표시명 | `_displayName` | 시트가 없을 때 보여줄 이름 | ✓ (폴백) |
| 로컬라이즈 키 | `_localizationKey` | 구글 시트의 행을 찾는 열쇠 | ✗ |

**표시는 항상 `DisplayName`/`Description`을 통합니다.** 시트가 로드되어 있으면 그쪽이 이기고, 없으면 기본 표시명 → 에디터 식별자 → 에셋 이름 순으로 내려갑니다. 어느 단계에서도 빈 문자열이 나오지 않으므로 이름 없는 칸이 생기지 않습니다.

키는 `item.{종류}.{식별자}` 규칙으로 **만들 때 한 번 채워지고 그 뒤로는 따라 바뀌지 않습니다.** 에셋 이름에서 매번 계산하면 이름을 바꾸는 순간 시트 행이 고아가 되고, 화면에는 조용히 폴백이 뜹니다. 빈 키와 중복 키는 `ItemDatabase` 인스펙터가 잡습니다.

이름과 설명은 **키 하나에서 접미사로 갈립니다.** `item.ammo.rustysmall` → `.name` / `.desc`.

아이템은 씬이 아니라 에셋에 있어서 씬을 훑는 등록으로는 걸리지 않습니다. `Tools > Localization > 아이템 이름·설명 표에 일괄 등록`이 따로 있고, SO 인스펙터에서도 한 개씩 등록할 수 있습니다.

**표에 넣을 값은 `FallbackName`/`RawDescription`이지 `DisplayName`이 아닙니다.** `DisplayName`은 이미 표를 거친 값이라, 영어로 보고 있는 중이면 영어가 한국어 칸에 들어갑니다.

### 로컬라이제이션

`Localization.Get(key, fallback)` 하나가 전부입니다. 표는 `ILocalizationTable`로 갈아끼웁니다.

```
LocalizationTableSO (Resources)      ← 지금
구글 시트에서 받아온 표               ← 나중, SetTable로 덮어씀
        │
        ▼
   Localization.Get(key, fallback)
        │
        ├──▶ LocalizedText        (화면에 박힌 고정 문구)
        └──▶ ItemDataSO.DisplayName (데이터에서 오는 이름)
```

**표가 없어도 지금부터 이 창구로 읽습니다.** 나중에 시트 로더를 꽂으면 호출부는 한 줄도 바뀌지 않습니다. 반대로 키를 나중에 끼우려 하면 모든 호출부를 다시 찾아야 합니다.

유니티 Localization 패키지를 쓰지 않은 이유는 **Addressables가 강제로 딸려오기 때문**입니다. 지금 필요한 건 "키로 문자열 찾기"뿐이고, Addressables는 [BACKLOG](BACKLOG.md)에서 아직 미뤄둔 항목입니다. 로케일별 폰트·에셋이나 복수형이 필요해지면 그때가 갈아탈 시점입니다 — 창구가 하나라 갈아타는 비용은 표 구현 하나입니다.

`LanguageType`은 표의 값 **배열 인덱스**라 0부터 빈틈없이 이어져야 합니다. 뒤에만 추가하세요.

### 고정 문구와 동적 문구

| | 방식 | 예 |
|---|---|---|
| 화면에 박힌 문구 | `LocalizedText` 컴포넌트 | "재장전 중", 슬롯 이름 |
| 숫자·기호만 | 로컬라이즈하지 않는다 | 잔탄 `12/30` |
| 값이 끼어드는 문장 | `Localization.Format(key, fallback, args)` | "남은 시간 {0:0.0}초" |
| 데이터에서 오는 이름 | `ItemDataSO.DisplayName` | 아이템·탄약 이름 |

**값이 끼어들면 표에 넣는 건 포맷 문자열입니다.** 코드에서 `"남은 시간 " + t + "초"`처럼 이어붙이면 번역이 아예 불가능해집니다 — 언어마다 어순도 단위 위치도 다릅니다. 조각이 아니라 문장 전체를 번역하게 합니다. 번역자가 중괄호를 깨먹는 건 반드시 생기므로 `Format`은 예외를 잡아 원문을 돌려줍니다.

**언어가 바뀌면 코드가 조립한 문구는 아무도 다시 그려주지 않습니다.** `UIPanelBase`가 `Localization.OnChangedEvent`를 구독해 `RefreshLocalization()`을 부르므로, 문자열을 만드는 패널만 그걸 오버라이드하면 됩니다.

`LocalizedText`는 **원문을 함께 들고 있습니다.** 표에 키가 없을 때 화면에 키 문자열 대신 원문이 뜨고, 에디터의 "원문을 표에 등록"이 그 값을 한국어 칸에 그대로 넣습니다. 그래서 텍스트를 적어두는 것만으로 표가 채워집니다.

키는 **버튼을 누른 그 순간에만** 계층 경로에서 계산합니다(`ui.maincanvas.parthud.popupreload.texttitle`). 매번 경로에서 계산하면 오브젝트를 옮기거나 이름을 바꾸는 순간 시트 행이 조용히 고아가 됩니다. 아이템 키와 같은 판단입니다.

TMP 인스펙터를 덮어쓰지 않고 **컴포넌트 ⋮ 메뉴의 `Localize`** 로 붙입니다. TMP 인스펙터를 상속해 갈아끼우면 TMP가 업데이트될 때마다 깨집니다.

표는 `Tools > Localization > 표 편집기`에서 키 × 언어 격자로 편집합니다. 기본 인스펙터로는 키를 찾을 수도, 어느 칸이 비었는지 볼 수도 없습니다 — 번역 작업은 "빠진 칸 찾기"가 대부분이라 그게 안 보이면 도구가 아닙니다.

구글 시트와는 **TSV로 오갑니다.** 시트에서 범위를 복사해 붙여넣거나, 여기서 복사해 시트에 붙이면 그대로 들어갑니다. 붙여넣기는 **있는 키를 갱신하고 없는 키를 추가할 뿐 지우지 않습니다** — 시트에서 일부만 복사해 온 경우 나머지가 통째로 날아갑니다. 값 안의 줄바꿈은 `\n`으로 escape합니다(TSV는 줄바꿈이 곧 행 구분입니다).

### 아이콘과 월드 스프라이트

같은 아이템이라도 UI에 그려질 때와 바닥에 떨어져 있을 때 쓰는 리소스가 다릅니다.

| | 필드 | 쓰는 곳 |
|---|---|---|
| UI 아이콘 | `IconSprite` | 인벤토리 칸, 드래그 고스트, 핫바 |
| 월드 스프라이트 | `WorldSprite` | `WorldItem` |

`WorldSprite`는 **비어있으면 `IconSprite`로 되돌아갑니다.** 아이콘 하나로 충분한 아이템이 대부분이라 필수로 두지 않았습니다.

**월드에 그릴 때는 반드시 `WorldSprite`를 통하세요.** `IconSprite`를 직접 읽는 경로가 하나라도 생기면, 전용 스프라이트를 지정해도 그 경로만 조용히 안 바뀝니다.

### 개체 상태

`ItemStack`은 `(itemId, count, instanceId)`입니다. 같은 아이템이라도 개체마다 달라지는 상태는 `ItemInstance`가 들고 있고, `ItemInstanceRegistry`(정적)가 보관합니다.

`ItemDataSO.RequiresInstance`가 true인 아이템만 인스턴스를 갖습니다 — 자원 수천 개에 객체를 붙이지 않기 위해서입니다. 그런 아이템은 인벤토리에서 **겹치지 않고 한 칸을 혼자 씁니다**. 넣을 때는 `Inventory.Add`가 아니라 `AddStack`을 쓰세요.

`EquipmentController`가 SO가 아니라 `ItemStack`을 들고 있는 이유도 `instanceId`를 잃지 않기 위해서입니다.

## 기체 파츠

기체는 **코어 / 좌팔 / 우팔 / 추진체** 네 슬롯입니다(`EquipSlotType`). 더 세분된 것(적재 용량, 전력량)은 슬롯을 늘리지 않고 **파츠의 하위 모듈로 내려갑니다.**

팔에 들어가는 것은 `PlayerWeaponDataSO`(또는 도구)이고, 코어·추진체는 `PartDataSO` 파생입니다. 무기를 `PartDataSO`로 묶지 않은 이유는 **스탯 체계가 다르기 때문**입니다 — 무기는 `WeaponStatus`를 따로 갖습니다.

### 장착이 스탯이 되는 지점

`EquipmentController`는 "어느 슬롯에 무엇이 끼워져 있는가"만 압니다. 그게 무슨 의미인지는 구독자가 정하고, **`MechaPartController`가 그 유일한 구독자**입니다.

```
EquipmentController.OnEquipChangedEvent
        │
        ▼
MechaPartController  ← PartDataSO.Deltas 를 AgentStatus modifier 로
```

**origin은 슬롯마다 다른 객체입니다**(`SlotOrigin`). `PartDataSO` 자신을 origin으로 쓰면 같은 파츠를 두 슬롯에 달았을 때 한쪽을 빼는 순간 양쪽이 같이 걷힙니다 — origin은 참조 동일성으로 비교되기 때문입니다.

교체든 해제든 **먼저 걷어내고 다시 겁니다.** 교체에서 제거를 빼먹으면 조용히 중첩됩니다.

**`Status<int>`에는 Percent를 걸 수 없습니다.** modifier 값이 int라서 0.2가 0으로 잘립니다(`StatusCombiner.CombineInt`). `MechaPartController`가 경고를 내고 건너뜁니다 — 조용히 틀리는 것보다 낫습니다.

**비주얼은 여기서 만들지 않습니다.** 스탯과 프리팹 생성을 한 클래스가 들면, 프리팹이 없는 파츠에서 스탯까지 같이 빠집니다. 아트가 안 나온 파츠로도 밸런스를 볼 수 있어야 합니다.

### 진입할 때 기체를 채우는 것

핫바가 없으므로 **`EquipmentController`가 비어 있으면 무장이 아예 생기지 않습니다.** `MechaLoadoutApplier`가 `MechaLoadoutSO`(구성표)를 읽어 채웁니다.

`AfterInitialize`가 아니라 **`Start`에서** 적용합니다. 컴포넌트 초기화 순서는 보장되지 않아서, `AfterInitialize`에서 장착하면 아직 구독하지 않은 컴포넌트가 장착 이벤트를 통째로 놓칩니다. (`MechaPartController`는 그래도 안전하도록 구독 직후 현재 상태를 한 번 훑습니다.)

**여기가 "새 판 시작" 지점입니다.** 월드 상태를 되돌릴 유일한 자리라 `ItemInstanceRegistry.Clear()`와 `GameRandom.Reseed()`를 같이 부릅니다. 안 부르면 플레이 모드를 들락거릴 때마다 이전 판의 인스턴스가 쌓입니다 — 정적이라 플레이 모드를 나가도 남습니다.

무기처럼 `RequiresInstance`인 아이템은 `ItemInstanceRegistry.CreateStack`으로 만듭니다. 그냥 `ItemStack`을 만들면 모딩·내구도가 붙을 자리가 없습니다.

## 무기 모딩

> ⚠ **구조가 일반화될 예정입니다.** 지금은 무기만 모딩할 수 있는데, 코어·추진체도 하위 모듈을 받게 됩니다(`ModdableItemInstance` 추출). 아래 규칙은 그대로 유지됩니다. ([PIVOT.md](PIVOT.md#용어))
>
> 용어 리네임은 끝났습니다 — 무기에 끼우는 것이 **모듈**, 기체를 구성하는 코어·팔·추진체가 **파츠**입니다.

무기 스탯은 **모든 스탯을 다 가지는 단일 클래스**입니다(`WeaponStatus`). 근접무기도 탄창 크기를 갖습니다. 호환 판정은 스탯 보유 여부가 아니라 **슬롯과 카테고리로 명시**하기 때문에 그래도 됩니다.

`WeaponStatType`을 배열 인덱스로 쓰므로 **enum 값이 0부터 빈틈없이 이어져야 합니다.** 중간에 끼워 넣지 말고 뒤에 추가하세요.

`WeaponStatus`는 **무기 인스턴스마다 따로** 만듭니다. SO는 여러 무기가 공유하므로 기본값만 읽어옵니다. 같은 소총 두 정에 다른 모듈을 끼울 수 있어야 합니다.

### 개량과 모듈의 차이

| | 개량 (`UpgradeSO`) | 모듈 (`ModuleDataSO`) |
|---|---|---|
| 성격 | 무기 자체를 단계별로 손봄 | 갈아끼움 |
| 트레이드오프 | 올리는 대신 떨굼 | 보통 순수 강화 |
| 단계 | 있음 (누적 아닌 **교체**) | 없음 |
| 제한 | 무기별 허용 목록 | 슬롯 + 카테고리 |
| origin | `UpgradeSO` 자신 | `ModuleDataSO` 자신 |

개량 단계가 **누적이 아니라 교체**인 이유: 누적하면 3단계쯤에서 실제 수치가 얼마인지 아무도 못 읽습니다.

모듈은 **스탯만 바꾸면 프리팹이 필요 없습니다.** 동작이 필요한 모듈(유탄 발사기 추가 등)만 `ModuleBehaviour` 프리팹을 등록합니다. 프리팹이면 동작·설정·비주얼이 한 덩어리로 갑니다.

**스탯 적용/해제는 프리팹 유무와 무관하게 `ModdingController` 한 곳에서만** 합니다. `ModuleBehaviour`는 동작과 비주얼만 담당합니다. 경로가 둘로 갈리면 "프리팹 있는 모듈만 해제 시 스탯이 안 돌아옴" 같은 버그가 반드시 납니다.

"연사 → 점사 전환" 정도는 모듈의 `AddFireModes`로 처리되므로 프리팹이 필요 없습니다.

### 모듈·개량의 주인은 WeaponItemInstance

**인벤토리에 들어있는(오브젝트가 없는) 무기도 모딩할 수 있어야 하므로**, 상태는 `WeaponItemInstance`가 갖습니다. 살아있는 `PlayerWeaponBase`는 그 상태를 따라가기만 합니다.

```
WeaponItemInstance   ← 모듈 / 개량 단계의 주인. 인벤토리에 있어도 편집 가능
        │ 이벤트
        ▼
ModdingController  ← 살아있는 무기에 반영 (스탯 modifier, 모듈 프리팹)
```

`WeaponItemInstance`는 `IItemSlotContainer`도 구현하므로, **인벤토리에서 모듈을 끌어다 모듈 칸에 놓는 게 별도 코드 없이 동작합니다.**

`ModdingController.Unbind()`는 **개체 상태를 건드리지 않습니다.** 거기서 모듈을 떼면 무기를 인벤토리에 넣는 순간 모딩이 통째로 날아갑니다.

장착하지 않은 무기의 최종 스탯은 `WeaponStatusBuilder.Build(instance)`로 계산합니다. 살아있는 무기와 UI 미리보기가 같은 결과를 내도록 계산 규칙을 한 곳에 모았습니다.

**미해결** — 모듈은 `ItemDataSO`라 Id가 있지만 `UpgradeSO`에는 Id가 없습니다. 저장 시스템을 붙일 때 개량을 `ItemDataSO` 파생으로 올리거나(도감에도 뜸) 별도 Id 체계를 두어야 합니다.

## 탄약

> ⚠ **재장전이 없어집니다.** 구경·탄종 두 층은 그대로 남고, 탄창이 사라져 적재함에서 **자동 급탄**합니다. `WeaponItemInstance`가 들고 있던 탄창 상태 중 장전 탄종만 남습니다. ([PIVOT.md](PIVOT.md#탄약))

두 층으로 나뉩니다. **구경은 "끼워지는가", 탄종은 "얼마나 잘 나가는가"입니다.**

| | 담당 | 형태 |
|---|---|---|
| `AmmoCaliberType` | 무기와 탄약이 맞는지 | enum |
| `AmmoDataSO` | 같은 구경 안에서의 성능 차이 | `ItemDataSO` 파생 |

구경을 enum으로 둔 이유는 개수가 정해져 있고 코드가 이름으로 지목할 일이 있기 때문입니다(CONVENTIONS의 키 선택 기준). 반면 탄종은 계속 늘어나므로 아이템 Id 체계에 올라탑니다. **새 구경은 뒤에만 추가하세요.**

### 성능 차이를 WeaponStatDelta로 표현한다

철갑탄(`Penetration +2`, `Damage -10%`), 고폭탄(`ExplosionRadius +1.5`), 소이탄 — 전부 모듈·개량과 **똑같은 `WeaponStatDelta` 목록**입니다. origin은 탄약 SO 자신입니다.

전용 필드(`damageMultiplier` 등)를 두지 않은 이유는 스탯 적용 경로가 둘로 갈리기 때문입니다. 한번 갈리면 "모듈은 반영되는데 탄약은 안 되는" 버그가 반드시 납니다. 적용은 모듈과 마찬가지로 **`ModdingController` 한 곳에서만** 합니다.

`WeaponStatusBuilder.ApplyAll`도 장전된 탄약을 포함하므로, UI 미리보기가 실제 성능과 같은 수치를 냅니다.

**스탯으로 표현되지 않는 것**(화상 부여, 폭발 연출, 예광 색)은 `AmmoDataSO.ProjectilePool`에 다른 투사체 프리팹을 지정해서 처리합니다. 프리팹이면 동작·설정·비주얼이 한 덩어리로 가고, 순수 스탯 탄은 비워두면 무기 기본 투사체를 씁니다. 모듈의 `BehaviourPrefab`과 같은 판단입니다.

### 탄창의 주인도 WeaponItemInstance

모듈·개량과 같은 이유입니다. 인벤토리에 넣었다 다시 들었을 때 반쯤 남은 탄창이 유지되어야 하고, 그대로 저장되어야 합니다.

```
WeaponItemInstance   ← LoadedAmmoId + AmmoInMagazine
        │ 이벤트
        ├──▶ ModdingController   ← 탄종이 바뀌면 스탯 modifier 교체
        └──▶ WeaponAmmoController  ← 재장전 진행 (오브젝트가 살아있는 동안만)
```

`WeaponAmmoController`가 `Inventory`를 직접 캐시하지 않고 `InventoryController`를 통해 매번 읽는 이유는 초기화 순서 때문입니다. `AfterInitialize`가 도는 순서는 정해져 있지 않아서, 무기가 먼저 서면 그 시점의 `Inventory`는 아직 null입니다.

**탄종을 바꿀 때 탄창에 남아있던 다른 탄은 인벤토리로 돌려줍니다.** 그냥 버리면 탄종을 한 번 바꿀 때마다 반 탄창씩 증발합니다. 인벤토리에 자리가 없으면 발밑에 떨굽니다.

## 발사와 투사체

```
PlayerRangedWeapon ──(발사 시점의 스탯을 값으로 복사)──▶ ProjectileLaunchData
                                                              │
                                                              ▼
                                                         Projectile
                                                              │ 매 프레임
                                                              ▼
                                                      ProjectileCaster ──▶ 이펙터
```

무기 스탯을 참조로 넘기지 않는 이유는, 총알이 날아가는 동안 무기를 바꾸거나 모듈을 갈아도 **이미 나간 탄의 위력이 변하면 안 되기** 때문입니다.

### +X가 앞이다

조준 피벗의 **+X가 항상 커서 방향**입니다(`PlayerAimController`). 발사 방향, 총구 위치, 모듈 장착점이 전부 이 규칙 하나 위에 서 있습니다.

리소스가 왼쪽을 보고 그려졌으면 `PlayerWeaponBase._spriteFacing`을 `Left`로 두세요. 무기를 통째로 X 미러링해서 규칙에 맞춰줍니다. **발사 방향에서 부호를 뒤집는 식으로 맞추지 마세요** — 규칙이 두 개가 되는 순간 스프라이트·총구·모듈이 따로 놉니다. ([INCIDENTS.md](INCIDENTS.md#총은-왼쪽을-보는데-총알은-오른쪽으로-나간다))

미러링은 두 축에서 각각 다른 이유로 일어납니다. 축이 다르고 대상이 다르므로 서로 간섭하지 않습니다.

| 축 | 대상 | 언제 | 이유 |
|---|---|---|---|
| X | 무기 (`PlayerWeaponBase`) | 스폰 시 한 번 | 리소스가 어느 쪽을 보고 그려졌는가 |
| Y | 조준 피벗 (`PlayerAimController`) | 조준 x의 부호가 바뀔 때 | 왼쪽을 볼 때 무기가 뒤집히지 않게 |

Y 미러링을 무기가 아니라 **피벗**에 거는 이유는 총구 오프셋 때문입니다. 총열 위(+Y)에 찍힌 총구는 무기가 뒤집히면 아래로 내려와야 맞는데, 피벗을 뒤집으면 스프라이트와 총구·모듈 장착점이 한꺼번에 따라옵니다.

위/아래를 정확히 겨누면 조준 x가 0 근처에서 떨리므로 `_facingDeadzone` 안에서는 마지막 방향을 유지합니다. 캐릭터 몸통처럼 같이 뒤집혀야 하는 것은 `PlayerAimController.IsFacingLeft`를 읽으면 됩니다.

### CastPower — Agent 스탯만으로는 부족하다

`DamageCastEffector`는 원래 `Owner.AgentStatus.Damage`를 씁니다. 그대로 두면 무기 스탯도 탄종 차이도 전혀 반영되지 않습니다. 그래서 `CasterBase.Power`(nullable)에 발사자가 계산한 위력을 실어 보내고, 이펙터는 그게 있으면 우선합니다. 없으면 기존 동작 그대로입니다.

### 왜 경로를 훑는가

원형 질의만 하면 빠른 탄이 한 프레임에 적을 통째로 지나쳐 버립니다(터널링). `ProjectileCaster`는 직전 위치에서 현재 위치까지를 `CircleCast`로 쓸어 담습니다.

관통도 여기 있습니다. `CasterBase`의 중복 제거는 **한 번의 Cast 안에서만** 유효해서, 프레임을 넘겨 같은 적을 다시 때리는 것은 막아주지 못합니다. `ProjectileCaster`가 맞힌 대상을 기억했다가 `CanAffect`로 걸러냅니다.

### 발사 모드

타이머는 코루틴이 아니라 `Update`로 돕니다. 무기는 핫바를 넘길 때마다 파괴되는데, 파괴 도중 코루틴이 살아있으면 **이미 없는 무기가 한 발 더 쏩니다.**

점사(`Burst`)는 묶음이 도는 동안 쿨타임을 보지 않고 `BurstInterval`로 돌다가, 묶음이 끝난 뒤에 `AttackCooltime`을 한 번 겁니다.

산탄 각도와 치명타는 **`GameRandom.Combat`** 을 씁니다. `UnityEngine.Random`은 프로세스 전역이라 멀티에서 클라마다 탄이 다른 곳으로 날아갑니다.

### 투사체 프리팹 구조

폭발 캐스터는 직격 캐스터의 **형제**여야 합니다. 자식으로 두면 `CasterBase`가 `GetComponentsInChildren`으로 상대의 이펙터까지 집어갑니다.

```
Projectile
 ├ HitCaster  (ProjectileCaster + DamageCastEffector)
 └ Explosion  (CircleCaster + DamageCastEffector [+ ConditionCastEffector])
```

## 조준

**마우스는 조준점의 절대 위치입니다.** FPS처럼 마우스 이동량으로 조준점을 미는 방식(상대 조준)을 쓰지 않습니다. 인벤토리가 커서를 그대로 쓰기 때문에, 커서를 잠그는 방식으로 가면 UI를 열고 닫을 때마다 입력 모드를 갈아타야 하고 그 경계에서 버그가 납니다.

그래서 조준점은 이렇게 만들어집니다.

```
커서 월드 좌표
   │ + 반동 오프셋 (발사 방향으로 밀렸다가 스스로 회복)
   │ 화면 안으로 자르기 (축별)
   ▼
AimPosition ──▶ AimDirection ──▶ 발사 / 무기 회전 / 조준점 / 카메라
```

**반동을 `AimPosition`에 직접 써넣으면 안 됩니다.** 다음 프레임에 마우스 값으로 덮여 사라집니다. 별도 오프셋으로 들고 있다가 더합니다.

이 모델의 결과를 분명히 해둡니다 — **반동은 스스로 회복하는 연출·명중률 효과이지, 플레이어가 마우스를 내려서 잡는 조작이 아닙니다.** 반동 제어를 실력 요소로 만들려면 상대 조준으로 가야 하고, 그건 커서 잠금과 입력 모드 전환을 동반합니다.

**무기 사거리로는 조준점을 자르지 않습니다.** 사거리 밖이라고 조준점을 안쪽에 붙들면 커서와 갈라져서 조작이 어긋난 것처럼 보입니다. 사거리 판정은 탄이 얼마나 날아가는지(`Range`)로만 합니다. `AimRange` 스탯은 카메라 거리나 명중률 감소 기준으로 쓰라고 남겨뒀고 **지금은 읽는 곳이 없습니다.**

### 화면 밖으로는 나가지 않는다

`AimPosition`은 카메라 뷰 안으로 잘립니다(`_viewPadding`).

커서는 원래 화면 안에 있으므로 **평소에는 걸리지 않습니다.** 반동으로 밀린 만큼과, 마우스가 게임 창 밖으로 나간 경우만 여기서 잡힙니다.

**여백은 비율이 아니라 거리입니다.** 비율(0.85 등)로 두면 화면이 클수록 여백이 같이 커집니다 — `orthographicSize 10`이면 가로로만 2.7유닛이 죽은 영역이 되고, 커서가 거기 들어가는 순간 조준점이 멈춰서 **커서에서 떨어져 나갑니다.**

카메라의 치우침 상한(`CameraFollowEffector._maxAimOffsetRatio`)도 같은 이유로 Vector2입니다. **둘 다 절대 거리가 아니라 각 축의 반너비/반높이에 대한 비율**이어야 합니다 — 절대 거리로 두면 해상도나 정조준 줌이 바뀌는 순간 다시 밖으로 나갑니다.

자를 때는 카메라의 **지난 프레임** 위치를 씁니다. 카메라는 `LateUpdate`에서 조준점을 따라오므로, 같은 프레임 값을 쓰면 서로를 참조하며 발산합니다.

### 정조준

> ⚠ **기능이 폐기됩니다.** 우클릭이 우무기 발사로 가기 때문입니다. `SetAiming`과 카메라 줌 기계장치는 **지우지 않고 입력 연결만 끊습니다** — 자동조준 모듈이나 저격형 코어가 재사용할 자리입니다.

우클릭입니다. **원래 우클릭에 물려 있던 `Use`는 F로 옮겼습니다.**

- 탄 퍼짐 × `_aimSpreadScale` (무기별 필드. 스탯이 아니라 모드 배율이라 `WeaponStatus`에 넣지 않습니다)
- 반동 킥이 절반 — 명중률만 좋아지면 체감이 약합니다
- 카메라가 확대

## 카메라

`CameraFollowEffector`가 **플레이어와 조준점 사이**를 봅니다. 플레이어를 정확히 따라가면 조준하는 쪽이 화면 가장자리라 멀리 있는 적이 안 보입니다. 치우치는 정도에는 상한(`_maxAimOffset`)이 있습니다 — 조준점을 멀리 끌고 가면 플레이어가 화면에서 밀려납니다.

### 순서가 어긋나면 조준점이 커서에서 밀린다

세 컴포넌트가 전부 `LateUpdate`에서 도는데, 유니티는 같은 단계 안의 호출 순서를 보장하지 않습니다. `AimExecutionOrder`로 값을 못박아 뒀습니다.

```
100  CameraFollowEffector  카메라가 먼저 움직인다 (지난 프레임 조준점을 향해)
200  PlayerAimController   옮겨간 카메라 기준으로 커서를 월드 좌표로
300  PlayerAimPoint        계산된 위치에 마커를 놓는다
```

조준을 `Update`에서 계산하면, 그 뒤 `LateUpdate`에서 카메라가 움직인 만큼 **조준점이 커서에서 밀립니다.** 카메라가 계속 이어서 따라오므로 밀린 채로 고정됩니다.

### 흔들림과 따라가기

**따라가기는 리그의 `position`을, 흔들림은 카메라의 `localPosition`을 건드립니다.** 둘이 같은 오브젝트에 있으면 매 프레임 서로를 덮어써서 흔들림이 아예 안 보입니다. 따라가기는 부모(리그), 흔들림은 자식(카메라)에 두세요. 같이 있으면 경고가 뜹니다.

## 생존 수치

> ⚠ **종류가 바뀝니다.** 스테미너 → **전력**, 허기·갈증 → **연료**. 구조(최대값은 스탯, 현재값은 컴포넌트, 고갈 시 페널티 + 지속 피해)는 그대로 재사용됩니다. ([PIVOT.md](PIVOT.md#전력과-연료))

`AgentStatus`가 **최대값**을, `VitalStatus`가 **현재값**을 갖습니다. `Health`와 같은 구조입니다 — 스탯은 "얼마까지 찰 수 있나"고, 컴포넌트는 "지금 얼마인가"입니다.

체력은 여기 들어가지 않습니다. 체력만 방어력·저항 계산을 타기 때문입니다.

**스테미너를 무엇이 쓰는지는 `VitalStatus`가 정하지 않습니다.** `TryConsumeStamina(amount)`를 부르는 쪽(지금은 질주)이 정합니다. 여기서 질주를 알게 되면 구르기·근접공격이 생길 때마다 이 파일을 고쳐야 합니다.

질주는 **입력(`_sprintHeld`)과 실제 상태(`_sprintActive`)를 나눠** 둡니다. 스테미너가 바닥나면 누르고 있어도 질주가 아닙니다. 제자리에서는 소모하지 않습니다 — 서서 Shift를 누르고 있다고 지치면 이상합니다.

바닥나면 **일정 비율까지 차야 다시 쓸 수 있습니다**(`_staminaRecoverThreshold`). 안 그러면 한 방울씩 차며 질주가 딸꾹질합니다.

허기·갈증이 0이면 **이동속도 페널티와 지속 피해가 둘 다** 들어갑니다. 페널티는 modifier라 켜고 끄는 순간에만 손대고, 피해는 `Health.ApplyDirectDamage`로 방어력을 무시합니다 — 갑옷을 입었다고 덜 굶지는 않습니다. 굶주림과 탈수는 **origin을 따로** 둬서 하나만 풀렸을 때 그것만 걷힙니다.

## 내구도와 아이템 사용

> ⚠ **소모품 사용이 폐기됩니다**(안전지대 수리만). `ItemUsability`와 내구도는 그대로 남고, `PlayerItemUseController`의 쿨타임 UI(`_cooldownFill`)는 **과열 게이지로 재활용**됩니다. "쿨타임은 `ItemUsability`가 보지 않는다"는 구분이 오버히트 락에 그대로 들어맞습니다.

내구도는 개체마다 달라야 하므로 `ItemInstance`(베이스)에 있습니다. 무기·도구·방어구가 전부 같은 자리를 씁니다.

`ItemDataSO.MaxDurability > 0`이면 **`RequiresInstance`가 자동으로 true**가 됩니다. 내구도가 있는데 개체 상태가 없으면 두 자루가 같은 내구도를 공유합니다.

**"지금 쓸 수 있나"는 `ItemUsability` 한 곳에서만 판정합니다.** 슬롯 표시(`_itemNotUseable`), 무기 발사, 사용 입력이 같은 답을 내야 합니다. 각자 판단하면 "표시는 멀쩡한데 안 쓰이는" 칸이 반드시 생깁니다.

**쿨타임은 여기 포함되지 않습니다.** 쿨타임은 기다리면 풀리는 것이고, `ItemUsability`가 보는 것은 손을 쓰지 않으면 영영 안 풀리는 상태입니다. 표시 방식도 달라야 합니다(`_itemNotUseable` vs `_cooldownFill`).

소모품 쿨타임은 **아이템 종류별**이고 `PlayerItemUseController`가 들고 갑니다. 개체별로 두면 칸을 나눠 담아 우회할 수 있고, 정적으로 두면 멀티에서 섞입니다.

## 손에 든 것이 입력을 해석한다

> ⚠ **전환에서 가장 크게 바뀌는 절입니다.** 좌우 무장이 동시에 활성이 되면서 좌클릭=좌무기 / 우클릭=우무기로 **고정 배분**되고, 각 손은 버튼 하나(`OnUse`)만 받습니다. 핫바·소모품·투척·정조준이 사라집니다. 배분표가 `PlayerHandController` 한 곳에만 있다는 원칙은 유지됩니다. ([PIVOT.md](PIVOT.md#입력))

입력은 **두 개뿐**입니다. 좌클릭(Primary)과 우클릭(Secondary). **무엇을 하는지는 입력이 정하지 않고 손에 든 것이 정합니다.**

| 든 것 | Primary(좌) | Secondary(우) |
|---|---|---|
| 총 | 발사 | 정조준 |
| 투척(신관) | 던지기 | 안전핀 제거 + 조준 |
| 소모품 | — | 사용 |
| 근접·도구 | (미정) | (미정) |

`Use` 액션은 없앴습니다. 우클릭 하나가 상황에 따라 조준이거나 사용입니다 — 아이템 종류가 늘 때마다 액션을 늘리면 바인딩이 서로를 잡아먹습니다.

```
PlayerInput ──▶ PlayerHandController ──▶ 현재 손 하나에게만 전달
                                          ├ PlayerRangedWeapon : HandActionBase
                                          ├ ThrowableHand      : ConsumableHand
                                          └ ConsumableHand     : HandActionBase
```

**구독하는 쪽이 각자 "내가 나설 차례인가"를 판단하면 안 됩니다.** 조건이 여러 곳에 흩어지고, 결국 둘 다 반응하거나 아무도 반응하지 않는 상태가 생깁니다. 라우터가 하나를 골라 그것에게만 넘깁니다.

손에 들 프리팹은 `IHandItemData`로 알려줍니다. 무기와 소모품은 상속 계보가 이미 갈려 있어 인터페이스로 뺐습니다 — 공통 베이스에 올리면 손에 들 일이 없는 자원·블럭까지 프리팹 칸을 갖게 됩니다.

### 상태를 어디에 두는가

> ⚠ **전제가 바뀝니다.** 핫바가 없어지고 교체가 안전지대에서만 일어나면 손 오브젝트는 **전투 중에 파괴되지 않습니다.** 그래서 과열 같은 런타임 상태를 `ItemInstance`에 올릴 필요가 없어집니다 — 무기 오브젝트가 그냥 들고 있으면 됩니다. 모듈·내구도처럼 인벤토리에서도 남아야 하는 것만 `ItemInstance`에 둡니다.

손 오브젝트는 **핫바를 넘길 때마다 파괴됩니다.** 그래서 무엇을 어디에 둘지가 갈립니다.

| 상태 | 위치 | 이유 |
|---|---|---|
| 안전핀 뽑힘 | `ThrowableHand` | 들고 있는 동안만 의미 있다. 칸을 넘기면 핀은 다시 꽂힌다 |
| 사용 쿨타임 | `PlayerItemUseController` | 손을 바꿔도 남아야 한다 |
| 정조준 | `PlayerAimController` | 카메라와 조준점도 봐야 하는 값이다 |
| 모듈·탄창·내구도 | `ItemInstance` | 인벤토리에 넣어도 남아야 한다 |

정조준을 무기가 직접 들면 무기를 바꾸는 순간 카메라가 확대된 채 굳습니다. 그래서 무기는 `_aim.SetAiming(true/false)`를 부르기만 합니다.

## 입력 차단

인벤토리를 열면 조준선이 사라지고 총이 나가지 않습니다. `UIInputBlocker`가 **세는 방식**으로 중간에 섭니다 — 인벤토리 위에 확인 창이 겹칠 수 있고, 하나만 닫혔다고 조작이 풀리면 안 됩니다.

`UIPanelBase._blocksGameplayInput`을 켠 패널이 뜨고 질 때 자동으로 밀고 뺍니다. 막는 쪽(패널)과 막히는 쪽(조준·발사)이 서로를 몰라도 됩니다.

**떼는 입력은 막지 않습니다.** 막힌 동안 뗀 것을 무시하면 버튼이 계속 눌린 상태로 남습니다. 막히기 시작하는 순간 `OnAttackReleased`를 대신 불러 연사와 차지를 풀어줍니다.

## 입력

`PlayerInput`은 SO이고 `Controls.IPlayerActions`를 구현해 **입력을 읽어 이벤트로 뿌리기만** 합니다. 게임 로직은 넣지 않습니다.

`OnDisable`에서 눌린 상태를 초기화합니다. SO는 플레이 모드를 나가도 살아있어서, 공격 버튼을 누른 채로 정지하면 다음 플레이에 눌린 상태로 시작합니다.

조준은 지금 마우스 전용입니다(`Look` 액션 없음). 패드 조준을 넣으려면 `Look`을 추가하고 `PlayerInput.PointerPosition` 자리를 갈아끼우세요.

**짧게/길게 누름 판정은 `PlayerInput`이 하지 않습니다.** 재장전 키는 눌림/뗌만 이벤트로 내보내고, "몇 초 이상이면 탄종 전환"은 `PlayerWeaponController`가 판단합니다. 시간 임계값은 게임 규칙이라 입력 리더에 들어가면 안 됩니다.

## 새 스크립트 하나만 임포트가 안 되고 CS0246이 난다

**증상** — 에디터 밖에서 만든 `.cs` 하나가 "타입을 찾을 수 없다"로 계속 걸립니다. 파일은 있고, `.meta`도 있고, 클래스명과 파일명도 맞고, 같이 만든 다른 파일은 멀쩡합니다.

**확인** — `Assembly-CSharp.csproj`에 그 파일만 빠져 있습니다. 유니티가 에셋으로 인식하지 못한 것이라 컴파일 대상에 아예 안 들어갑니다.

```bash
grep -c "내파일.cs" Assembly-CSharp.csproj   # 0 이면 이 경우
```

**안 통하는 것** — `Assets/Refresh`, 재컴파일 반복, `.meta` 삭제 후 재생성. `.meta`를 지워도 유니티가 `Library/metadata` 캐시에서 **같은 GUID를 되살려** 깨진 상태가 그대로 돌아옵니다.

**대응** — **파일과 클래스 이름을 바꿉니다.** 새 이름은 캐시에 없어서 깨끗하게 임포트됩니다. (`PartView` → `MechaPartView`로 해결했습니다)

유니티를 껐다 켜면 풀릴 수도 있지만, 이름을 바꾸는 쪽이 빠르고 확실합니다.

## ~~MCP로 메뉴 아이템을 못 부른다~~ (mcp-unity 시절)

> **2026-11-15에 MCP 서버를 바꿨습니다.** 아래는 `CoderGamester/mcp-unity`에서 겪은 일입니다.
> `CoplayDev/unity-mcp`는 `execute_code`로 파일을 만들지 않고 코드를 돌리므로 이 경로 자체가 없어졌습니다.
> 다만 **메뉴 경로를 ASCII로 짓는 습관은 유지하세요** — 자동화에서 한글 경로는 여전히 위험합니다.

**증상** — `execute_menu_item`이 `ExecuteMenuItem failed because there is no menu named '...'`로 실패합니다. 메뉴는 분명히 에디터에 떠 있습니다.

**원인이 두 가지라 섞입니다.**

1. **경로에 ASCII가 아닌 글자가 있으면 매칭에 실패합니다.** `Tools/Localization/표 편집기`처럼 한글이 들어간 메뉴는 MCP로 부를 수 없습니다. `&`도 쓰지 마세요 — 유니티가 단축키 지정자로 먹습니다.
2. **새로 만든 메뉴는 컴파일을 두 번 돌려야 잡힙니다.** 에디터 밖에서 `.cs`를 만들면 (a) 임포트 (b) 컴파일 + 도메인 리로드가 따로 일어납니다. 파일을 만든 직후의 `recompile_scripts`는 아직 임포트되지 않은 파일을 보지 못합니다.

**대응** — 자동화로 부를 메뉴는 **경로를 ASCII로** 짓습니다(`Tools/Item Database/Rebuild`). 새 에디터 스크립트를 만들었으면 `recompile_scripts` → `Assets/Refresh` → `recompile_scripts` 순으로 한 번 더 돌린 뒤에 호출하세요.

**왜 헷갈리나** — `recompile_scripts`가 두 경우 모두 "0 warnings"로 성공을 보고합니다. 컴파일은 실제로 성공했고, 실패한 것은 메뉴 조회입니다. 실패 원인은 콘솔에만 남으므로 `get_console_logs`를 보세요.

## 총은 왼쪽을 보는데 총알은 오른쪽으로 나간다

**증상** — 조준 방향이 반대로 나오는 것처럼 보입니다. 무기 스프라이트는 한쪽을 보고 있는데 투사체는 반대로 날아갑니다.

**원인** — 리소스가 **총구가 왼쪽(-X)을 향하게** 그려져 있었습니다. 코드는 전부 "+X가 앞"이라는 하나의 규칙 위에 서 있습니다 — `PlayerAimController`가 조준 피벗의 +X를 커서로 돌리고, 발사 방향도 그 규칙을 씁니다.

실제로 **총알은 처음부터 커서 쪽으로 제대로 날아가고 있었습니다.** 반대로 그려진 건 스프라이트 쪽이고, 총구(`_muzzle`)도 로컬 -X에 찍혀 있어서 투사체가 플레이어 **뒤에서** 생기고 있었습니다. 그래서 방향이 뒤집힌 것처럼 보였습니다.

**대응** — `PlayerWeaponBase._spriteFacing`(`WeaponFacingType`)에 리소스 방향을 명시하고, `Left`면 무기를 통째로 X 미러링해 +X를 앞으로 맞춥니다. 스프라이트와 총구·파츠 장착점이 한꺼번에 따라옵니다.

**발사 방향에서 부호를 뒤집어 맞추지 마세요.** 그러면 스프라이트는 여전히 반대를 보고, 총구는 뒤에 남고, 파츠 장착점과 이펙트 방향이 전부 따로 놉니다. 리소스와 코드의 규칙 차이는 **한 곳에서 한 번만** 흡수합니다.

> 방향이 이상하면 먼저 **총구의 로컬 X 부호**를 보세요. 음수면 리소스가 왼쪽을 보고 있는 것입니다.

**이어진 문제** — X를 맞추고 나면 왼쪽을 조준할 때 무기가 위아래로 뒤집힙니다. 피벗의 +X를 커서로 돌리면 +Y가 아래를 향하기 때문입니다. `PlayerAimController._keepUpright`가 조준 x의 부호에 따라 **피벗의** Y를 미러링해서 세워둡니다.

무기가 아니라 피벗을 뒤집는 이유는 총구 오프셋 때문입니다. 총열 위(+Y)에 찍힌 총구는 무기가 뒤집히면 아래로 내려와야 맞습니다.

## 잠든 Rigidbody2D에는 `OnTriggerStay2D`가 오지 않는다

**증상** — 아이템 위를 지나가면 주워지는데, **가만히 서 있으면 안 주워진다.** 다시 움직이면 주워진다.

**원인** — Rigidbody2D는 일정 시간 움직이지 않으면 잠든다(sleep). 잠든 바디에는 `OnTriggerStay2D`가 호출되지 않는다.

**대응** — 감지 주체를 뒤집었다. 아이템이 트리거로 기다리는 대신 **줍는 쪽이 `Physics2D.OverlapCircle`로 주기적으로 훑는다**(`ItemPickupSensor`). 물리 상태에 의존하지 않고, 줍기 반경도 히트박스와 무관하게 정할 수 있다.

`sleepMode = NeverSleep`으로도 막을 수 있지만, 그러면 모든 대상에 그 설정을 기억해야 한다.

## csproj가 오래되어 새 파일이 빌드에 빠진다

**증상** — 새 스크립트를 만든 직후 IDE가 `The type or namespace name 'X' could not be found` 에러를 도배하는데, 유니티 콘솔은 멀쩡합니다. 반대로 `dotnet build Assembly-CSharp.csproj`가 통과해도 새 파일은 검사되지 않은 것입니다.

**원인** — `.csproj`는 유니티가 생성합니다. 파일을 추가해도 유니티가 한 번 갱신하기 전까지 `<Compile Include>` 목록에 없습니다.

**대응** — 유니티 에디터에 포커스를 줘서 갱신시키거나, 검증용 csproj를 만들어 글롭으로 컴파일합니다.

```powershell
# Assembly-CSharp.csproj를 복사해 Compile 항목을 지우고 글롭으로 교체,
# 상대 HintPath를 절대 경로로 바꾼 뒤 빌드
$src = Get-Content 'Assembly-CSharp.csproj' -Raw
$src = [regex]::Replace($src, '\s*<Compile Include="[^"]*" />', '')
$src = [regex]::Replace($src, '<HintPath>(?![A-Za-z]:)([^<]+)</HintPath>', { param($m) '<HintPath>C:\경로\' + $m.Groups[1].Value + '</HintPath>' })
# </Project> 앞에 <Compile Include="...\Assets\01.Scripts\**\*.cs" /> 삽입
```

에디터 어셈블리는 따로 확인해야 합니다. 런타임 글롭에서 `**\Editor\**`를 제외하고, 에디터 검증에는 전부 포함시키세요.

## Unity 오브젝트에 `?.`를 쓰면 파괴된 객체를 통과시킨다

**원인** — 유니티는 `Destroy`된 객체에 대해 `==` 연산자를 오버로드해 "가짜 null"을 만듭니다. `?.`는 진짜 참조만 보므로 이 오버로드를 건너뜁니다.

**대응** — `if (x != null)`로 명시적으로 검사합니다. Rider/VS 분석기가 `Unity objects should not use null propagation`으로 잡아줍니다.

`Status<T>` 같은 순수 C# 객체에는 `?.`를 써도 됩니다.

## SO 에셋을 Ctrl+D로 복제하면 Id까지 복사된다

**증상** — 아이템 SO를 복제해 새 아이템을 만들었더니 원본과 Id가 같아집니다. 아이템 만들 때 복제가 가장 흔한 작업이라 자주 발생합니다.

**대응** — 세 겹으로 막습니다.

1. **복제 즉시 경고** — `ItemIdConflictWatcher`(AssetPostprocessor)가 임포트된 아이템의 Id가 이미 쓰이고 있으면 콘솔에 띄웁니다. Ctrl+D는 어떤 코드도 거치지 않아서, 이게 없으면 한참 뒤에 "인벤토리가 엉뚱한 아이템을 꺼낸다"로 발견합니다. **고치지는 않습니다** — 임포트 중에 에셋을 말없이 바꾸면 대량 리임포트 때 무슨 일이 났는지 알 수 없습니다.
2. **ItemDatabase 인스펙터의 「Id 충돌 해결」** — 누가 번호를 지키고 누가 새로 받는지 먼저 보여준 뒤 정리합니다.
3. **`Rebuild`가 항상 정리** — 원본이 자기 Id를 먼저 차지하도록 정렬합니다.

"원본"의 기준은 **DB가 지금 그 Id로 해석하고 있는 에셋**입니다(`ItemDatabaseBuilder.BuildOwners`). 파일 수정 시각은 git 체크아웃 한 번에 뒤바뀌므로 쓰지 않습니다.

```csharp
// 게임이 지금 실제로 해석하는 쪽을 그대로 둔다. 가장 덜 놀랍다.
assets.Sort((a, b) => {
    int aOwner = IsOwner(owners, a) ? 0 : 1;
    ...
});
```

**복제본이 진짜 새 아이템인 경우가 정상입니다.** 아이템을 만드는 가장 흔한 방법이 복제라서, 충돌이 났다고 지우면 안 됩니다. 복제본에 새 Id를 주는 것이 맞습니다.

같은 이유로 커서를 대역마다 따로 저장합니다. "최대값 + 1"로 계산하면 마지막 아이템을 지운 순간 그 Id가 재사용됩니다.

## `.gitignore`의 `*.so`가 `Assets/08.SO/` 폴더를 통째로 삼켰다

**증상** — `git status`에 SO 에셋이 한 번도 나타나지 않았습니다. `git mv`는 "not under version control"이라고 답했습니다. **아이템·탄약·모듈·코어·로드아웃 SO 38개가 전부 버전 관리 밖에 있었습니다.**

**원인** — 유니티 표준 `.gitignore`의 C++ 절에 있는 `*.so`(네이티브 공유 라이브러리)입니다. Windows의 git은 기본적으로 대소문자를 가리지 않으므로 이 패턴이 **폴더 이름 `08.SO`에 그대로 맞습니다.** 패턴 하나가 디렉터리를 가리면 그 아래는 통째로 제외되고, 안쪽을 다시 포함시키는 규칙도 먹지 않습니다.

**대응** — `.gitignore` 끝에 `!Assets/08.SO/`와 `!Assets/08.SO/**`를 함께 넣었습니다. 디렉터리 자체의 제외를 먼저 풀어줘야 안쪽 예외가 적용됩니다.

**교훈** — 폴더 이름에 확장자처럼 보이는 꼬리를 붙이지 마세요(`08.SO`, `03.Prefabs`는 안전하지만 `.a`, `.o`, `.so`, `.dll`로 끝나는 것은 전부 위험합니다). 그리고 **새 에셋 폴더를 만들면 `git status`에 실제로 나타나는지 한 번 확인하세요.** 안 나타나는 것은 "변경이 없다"와 구별되지 않습니다.

## 화면 흔들림이 한 번도 동작한 적 없었다

**증상** — `CameraShakeEffector`가 있고, `Shake()`를 불러도 화면이 흔들리지 않습니다. **에러도 경고도 없습니다.**

**원인** — 흔들림은 `transform.localPosition`(자기 자신)을 건드리는데, 그 컴포넌트는 `CameraManager`에 붙어 있고 **카메라는 그 자식이 아니었습니다.** 따라가기(`CameraFollowEffector`)는 `_rig` 참조로 `MainCamera`를 직접 움직이고 있었으니, 둘은 서로 다른 오브젝트를 보고 있었고 흔들림 쪽은 아무것도 아닌 것을 흔들고 있었습니다.

코드에 "따라가기는 리그에, 흔들림은 카메라에 두세요"라는 경고까지 있었지만, 그 검사는 **같은 GameObject에 둘 다 있는 경우만** 봅니다. 지금처럼 둘 다 같은 GameObject에 있었는데도 경고가 안 뜬 이유는 `_rig`가 다른 오브젝트를 가리켜서 검사를 통과했기 때문입니다.

**대응** — `CameraShakeEffector`에 `_target`을 두고, 씬을 `CameraRig`(따라가기) → `MainCamera`(흔들림)로 나눴습니다. 대상이 비어 있으면 경고를 남깁니다.

**교훈** — **"아무 일도 안 일어나는데 에러도 없는" 연출은 호출부가 아니라 대상을 의심하세요.** Transform을 건드리는 컴포넌트는 "무엇을 움직이는가"가 인스펙터에 드러나야 합니다. `transform`을 기본값으로 쓰면 계층이 바뀌는 순간 조용히 빗나갑니다.

## 에디터가 비활성이면 플레이 모드가 돌지 않는다 (MCP로 검증할 때)

**증상** — MCP로 플레이 모드를 켜고 상태를 읽으면 **매번 똑같은 값**이 돌아옵니다. 위치도 속도도 그대로이고, `didStart`는 true인데 아무것도 진행되지 않습니다. 코드가 안 도는 것처럼 보입니다.

**원인** — 유니티 에디터는 포커스를 잃으면 기본적으로 플레이 모드를 멈춥니다(Run In Background 꺼짐). MCP 요청은 백그라운드에서 오므로 **첫 프레임만 돌고 멈춘 상태**를 계속 읽게 됩니다.

**대응** — 플레이 모드에 들어간 뒤 `execute_code`로 `Application.runInBackground = true;`를 한 번 실행합니다. 그 뒤로는 포커스가 없어도 시간이 흐릅니다(플레이 모드를 나가면 원래대로). (2026-11-15, CoplayDev MCP에서 확인)

옛 MCP(`mcp-unity`)에서는 `set_play_mode_status`의 `step`을 `batch_execute`로 100개씩 넣어 프레임을 넘겼습니다.

**교훈** — 값이 두 번 연속 완전히 같으면 **로직을 의심하기 전에 시간이 흐르고 있는지**를 확인하세요. 멈춘 것과 안 움직이는 것은 구별되지 않습니다. 스텝으로 넘겨서 값이 바뀌면 로직은 멀쩡한 것입니다.

## 단발 무기를 든 AI가 한 발만 쏘고 멈춘다

**증상** — 적 기체가 무기를 달고 사정권에 섰는데 쏘지 않습니다. 에러도 경고도 없고, 트리거는 당겨져 있습니다.

**원인** — `OnUsePressed`를 **잡고만** 있었습니다. 연사(`Auto`)는 `Update`에서 스스로 다음 발을 쏘지만, **단발·점사는 눌렀다 떼야** 다음 발이 나가고 차지는 떼는 순간 나갑니다. 사람 손은 자연스럽게 떼지만 AI는 안 뗍니다.

**대응** — `HandActionBase`에 `HoldsTrigger` / `TriggerHoldTime`을 두어 **무기가 자기 방식을 알려주게** 했습니다. `EnemyHandController`가 그에 맞춰 누르고 뗍니다.

**교훈** — "쏴라"와 "방아쇠를 당겨라"는 다릅니다. 입력을 흉내내는 AI를 붙일 때, **입력의 모양(누름/뗌/유지)이 의미를 갖는 곳**을 먼저 찾아야 합니다.

## 구경이 안 맞는 무기는 조용히 한 발도 안 나간다

**증상** — 적이 무기를 들고 사정권에서 방아쇠를 당기는데 탄이 안 나갑니다. **에러도 경고도 없습니다.**

**원인** — 무기 구경(`AmmoCaliberType`)에 맞는 탄약 에셋이 없었습니다. `Hunter`는 `Middle`, `Burster`는 `Buckshot`을 쓰는데 탄약 에셋은 `Small`과 `Heavy`뿐이었습니다. `WeaponAmmoController`는 호환 탄을 찾지 못하면 `CanFire`를 false로 돌리고 조용히 끝냅니다 — 플레이어라면 UI로 보이지만 적은 아무 흔적도 남기지 않습니다.

**대응** — `MechaLoadoutTableSO.HasAmmoFor`로 "이 표의 적재품으로 먹일 수 있는 무기인가"를 판정하고, `OnValidate`가 표를 짤 때 경고합니다. 적 구성 후보도 그 기준으로 걸러서 넣습니다.

**교훈** — 조립은 되는데 **쓸 수 없는 조합**이 만들어지는 자리를 경계하세요. 슬롯 호환(`AllowedSlots`)만 보면 "달리긴 하는데 작동하지 않는" 기체가 나옵니다.

## 버린 아이템이 0.5초 뒤 다시 주워진다 (2026-11-25)

**증상** — 인벤토리에서 버리면(패널 밖·우클릭) 아이템이 발밑에 떨어졌다가 곧바로 적재함으로 돌아왔다. 버리기가 "안 되는" 것처럼 보인다.

**원인** — 줍기가 자동(`InventoryController.Scan`)이고, 떨군 아이템의 줍기 지연(`WorldItem._pickupDelay` 0.5초)이 끝나면 아직 발밑에 서 있는 그 사람이 다시 줍는다.

**대응** — 버린 사람은 **줍기 반경을 한 번 벗어나야** 다시 줍는다(`WorldItem.IgnorePickupBy`). 다른 사람은 바로 줍는다. 아이템을 떨구는 새 경로를 만들 때는 `ItemDiscard`를 거치거나 같은 처리를 할 것(분해 넘침 `ItemDisassembly`도 그렇게 함).

## 플레이 모드 검증은 `EditorApplication.Step`으로 프레임을 민다 (2026-11-25)

에디터가 비활성이면 시간이 안 흐른다(위). 그때는 `execute_code`에서 `EditorApplication.isPaused = true; EditorApplication.Step();`으로 **한 번 부를 때 한 프레임**씩 민다. 긴 타이머는 검증용으로 짧게 바꿔(리플렉션) 몇 번만 밀면 된다. 끝나면 `isPaused = false`로 되돌릴 것.

## ~~컴포넌트 속성 덤프에서 참조형이 null로 나온다~~ (mcp-unity 시절)

> **2026-11-15에 MCP 서버를 바꿨습니다.** 이건 `CoderGamester/mcp-unity`의 리플렉션 덤프 문제로 보입니다.
> `CoplayDev/unity-mcp`는 컴포넌트 단위 리소스로 읽으므로 같은 함정이 생길 구조가 아닙니다.
> 그래도 **교훈은 남습니다** — 도구가 돌려준 값과 실제 런타임 상태가 다를 수 있습니다.

**증상** — `get_gameobject`로 읽은 컴포넌트 속성에서 `Status`, `Ammo`, `Instance`, `Inventory`, `Core` 같은 **참조형 프로퍼티가 전부 null**로 나왔습니다. 그런데 바로 뒤에 설정되는 값(`CurrentFireMode`)은 제대로 들어 있고, 다시 읽으면 null이 아닌 때도 있었습니다.

**대응** — **null로 나온 참조형을 근거로 원인을 추정하지 마세요.** 확실한 것은 콘솔 로그와 실제 예외 스택입니다. 상태를 알아야 하면 로그를 심어서 확인하는 쪽이 빠릅니다.

이 함정으로 "초기화가 안 됐다"고 몇 번이나 잘못 짚었고, 실제 원인은 전혀 다른 곳(구경 불일치)에 있었습니다.

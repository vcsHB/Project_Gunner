## 총은 왼쪽을 보는데 총알은 오른쪽으로 나간다

**증상** — 조준 방향이 반대로 나오는 것처럼 보입니다. 무기 스프라이트는 한쪽을 보고 있는데 투사체는 반대로 날아갑니다.

**원인** — 리소스가 **총구가 왼쪽(-X)을 향하게** 그려져 있었습니다. 코드는 전부 "+X가 앞"이라는 하나의 규칙 위에 서 있습니다 — `PlayerAimController`가 조준 피벗의 +X를 커서로 돌리고, 발사 방향도 그 규칙을 씁니다.

실제로 **총알은 처음부터 커서 쪽으로 제대로 날아가고 있었습니다.** 반대로 그려진 건 스프라이트 쪽이고, 총구(`_muzzle`)도 로컬 -X에 찍혀 있어서 투사체가 플레이어 **뒤에서** 생기고 있었습니다. 그래서 방향이 뒤집힌 것처럼 보였습니다.

**대응** — `PlayerWeaponBase._spriteFacing`(`WeaponFacingType`)에 리소스 방향을 명시하고, `Left`면 무기를 통째로 X 미러링해 +X를 앞으로 맞춥니다. 스프라이트와 총구·파츠 장착점이 한꺼번에 따라옵니다.

**발사 방향에서 부호를 뒤집어 맞추지 마세요.** 그러면 스프라이트는 여전히 반대를 보고, 총구는 뒤에 남고, 파츠 장착점과 이펙트 방향이 전부 따로 놉니다. 리소스와 코드의 규칙 차이는 **한 곳에서 한 번만** 흡수합니다.

> 방향이 이상하면 먼저 **총구의 로컬 X 부호**를 보세요. 음수면 리소스가 왼쪽을 보고 있는 것입니다.

**이어진 문제** — X를 맞추고 나면 왼쪽을 조준할 때 무기가 위아래로 뒤집힙니다. 피벗의 +X를 커서로 돌리면 +Y가 아래를 향하기 때문입니다. `PlayerAimController._keepUpright`가 조준 x의 부호에 따라 **피벗의** Y를 미러링해서 세워둡니다.

무기가 아니라 피벗을 뒤집는 이유는 총구 오프셋 때문입니다. 총열 위(+Y)에 찍힌 총구는 무기가 뒤집히면 아래로 내려와야 맞습니다.

## 잠든 Rigidbody2D에는 `OnTriggerStay2D`가 오지 않는다

**증상** — 아이템 위를 지나가면 주워지는데, **가만히 서 있으면 안 주워진다.** 다시 움직이면 주워진다.

**원인** — Rigidbody2D는 일정 시간 움직이지 않으면 잠든다(sleep). 잠든 바디에는 `OnTriggerStay2D`가 호출되지 않는다.

**대응** — 감지 주체를 뒤집었다. 아이템이 트리거로 기다리는 대신 **줍는 쪽이 `Physics2D.OverlapCircle`로 주기적으로 훑는다**(`ItemPickupSensor`). 물리 상태에 의존하지 않고, 줍기 반경도 히트박스와 무관하게 정할 수 있다.

`sleepMode = NeverSleep`으로도 막을 수 있지만, 그러면 모든 대상에 그 설정을 기억해야 한다.

## csproj가 오래되어 새 파일이 빌드에 빠진다

**증상** — 새 스크립트를 만든 직후 IDE가 `The type or namespace name 'X' could not be found` 에러를 도배하는데, 유니티 콘솔은 멀쩡합니다. 반대로 `dotnet build Assembly-CSharp.csproj`가 통과해도 새 파일은 검사되지 않은 것입니다.

**원인** — `.csproj`는 유니티가 생성합니다. 파일을 추가해도 유니티가 한 번 갱신하기 전까지 `<Compile Include>` 목록에 없습니다.

**대응** — 유니티 에디터에 포커스를 줘서 갱신시키거나, 검증용 csproj를 만들어 글롭으로 컴파일합니다.

```powershell
# Assembly-CSharp.csproj를 복사해 Compile 항목을 지우고 글롭으로 교체,
# 상대 HintPath를 절대 경로로 바꾼 뒤 빌드
$src = Get-Content 'Assembly-CSharp.csproj' -Raw
$src = [regex]::Replace($src, '\s*<Compile Include="[^"]*" />', '')
$src = [regex]::Replace($src, '<HintPath>(?![A-Za-z]:)([^<]+)</HintPath>', { param($m) '<HintPath>C:\경로\' + $m.Groups[1].Value + '</HintPath>' })
# </Project> 앞에 <Compile Include="...\Assets\01.Scripts\**\*.cs" /> 삽입
```

에디터 어셈블리는 따로 확인해야 합니다. 런타임 글롭에서 `**\Editor\**`를 제외하고, 에디터 검증에는 전부 포함시키세요.

## Unity 오브젝트에 `?.`를 쓰면 파괴된 객체를 통과시킨다

**원인** — 유니티는 `Destroy`된 객체에 대해 `==` 연산자를 오버로드해 "가짜 null"을 만듭니다. `?.`는 진짜 참조만 보므로 이 오버로드를 건너뜁니다.

**대응** — `if (x != null)`로 명시적으로 검사합니다. Rider/VS 분석기가 `Unity objects should not use null propagation`으로 잡아줍니다.

`Status<T>` 같은 순수 C# 객체에는 `?.`를 써도 됩니다.

## SO 에셋을 Ctrl+D로 복제하면 Id까지 복사된다

**증상** — 아이템 SO를 복제해 새 아이템을 만들었더니 원본과 Id가 같아집니다. 아이템 만들 때 복제가 가장 흔한 작업이라 자주 발생합니다.

**대응** — 세 겹으로 막습니다.

1. **복제 즉시 경고** — `ItemIdConflictWatcher`(AssetPostprocessor)가 임포트된 아이템의 Id가 이미 쓰이고 있으면 콘솔에 띄웁니다. Ctrl+D는 어떤 코드도 거치지 않아서, 이게 없으면 한참 뒤에 "인벤토리가 엉뚱한 아이템을 꺼낸다"로 발견합니다. **고치지는 않습니다** — 임포트 중에 에셋을 말없이 바꾸면 대량 리임포트 때 무슨 일이 났는지 알 수 없습니다.
2. **ItemDatabase 인스펙터의 「Id 충돌 해결」** — 누가 번호를 지키고 누가 새로 받는지 먼저 보여준 뒤 정리합니다.
3. **`Rebuild`가 항상 정리** — 원본이 자기 Id를 먼저 차지하도록 정렬합니다.

"원본"의 기준은 **DB가 지금 그 Id로 해석하고 있는 에셋**입니다(`ItemDatabaseBuilder.BuildOwners`). 파일 수정 시각은 git 체크아웃 한 번에 뒤바뀌므로 쓰지 않습니다.

```csharp
// 게임이 지금 실제로 해석하는 쪽을 그대로 둔다. 가장 덜 놀랍다.
assets.Sort((a, b) => {
    int aOwner = IsOwner(owners, a) ? 0 : 1;
    ...
});
```

**복제본이 진짜 새 아이템인 경우가 정상입니다.** 아이템을 만드는 가장 흔한 방법이 복제라서, 충돌이 났다고 지우면 안 됩니다. 복제본에 새 Id를 주는 것이 맞습니다.

같은 이유로 커서를 대역마다 따로 저장합니다. "최대값 + 1"로 계산하면 마지막 아이템을 지운 순간 그 Id가 재사용됩니다.

## 탭이 0개일 때 `GUILayout.Toolbar`가 매 프레임 항목을 만든다

**증상** — Pool Manager 창을 처음 열면 그룹이 무한히 생성됩니다.

**원인** — `Toolbar(selected, texts)`는 **클릭이 없으면 `selected`를 그대로 반환**합니다. 탭이 0개면 `["+"]` 하나뿐이고 `selected`도 0이라, "+"가 눌린 것과 구분이 안 됩니다.

**대응** — 항목이 0개일 때는 `Toolbar` 대신 일반 `Button`을 그립니다.

## 인스펙터 전용 필드에 CS0649 경고가 뜬다

**원인** — 유니티 직렬화로만 채워지는 필드는 컴파일러가 보기에 "할당된 적 없음"입니다.

**대응** — 해당 블록만 `#pragma warning disable CS0649` / `restore`로 감쌉니다. 프로젝트 전역으로 끄지 마세요.

## `Dictionary.Add`가 중복 키로 터진다

**증상** — 같은 타입 컴포넌트가 오브젝트에 둘 붙어 있으면 `Agent.Awake`가 예외를 던집니다.

**대응** — `TryAdd`를 쓰고, 필요하면 경고를 남깁니다. 조용히 첫 번째만 등록하는 게 씬 전체가 안 뜨는 것보다 낫습니다.

## `WeaponStatus`가 SO 기본값을 공유하면 안 된다

**증상** — 같은 소총 두 정에 파츠를 끼우면 서로 영향을 줍니다.

**원인** — SO는 에셋이라 모든 인스턴스가 공유합니다.

**대응** — SO에는 `WeaponStatDefaults`(순수 값)만 두고, `WeaponStatus`는 무기 인스턴스마다 새로 만듭니다. 같은 이유로 SO에 런타임 상태를 두면 플레이 모드를 나가도 값이 남습니다.

## 히트박스를 나누면 데미지가 여러 번 들어간다

**증상** — 폭발이 적 하나에게 3번 적중합니다.

**원인** — `OverlapCircle`이 같은 유닛의 머리·몸통·다리 콜라이더를 각각 돌려줍니다.

**대응** — `CasterBase`가 콜라이더 목록을 `TargetBase` 기준으로 접습니다. 같은 대상이 여러 부위로 걸리면 **배율이 가장 높은 부위만** 남깁니다.

## 인터페이스만으로는 `gameObject`에 접근할 수 없다

**증상** — `IPoolable.SelfObject`를 구현체마다 똑같이 써야 했습니다.

**원인** — 인터페이스에는 필드가 없습니다.

**대응** — `PoolableMono` 추상 MonoBehaviour를 짝으로 만들었습니다. 같은 이유로 `ITargetable` 대신 `TargetBase` 클래스를 택했습니다. **인터페이스에 상태가 필요해지는 순간 클래스가 필요하다는 신호입니다.**

## 입력 액션을 바꾸면 `IPlayerActions` 구현이 깨진다

**증상** — `.inputactions`에서 액션을 추가/삭제하면 `PlayerInput`이 인터페이스 미구현으로 컴파일되지 않습니다.

**대응** — 액션을 편집한 뒤에는 `PlayerInput`의 콜백 목록을 반드시 맞춥니다. 쓰지 않는 액션도 빈 메서드로 둬야 합니다.

액션을 지웠다면 그 값을 쓰던 코드도 같이 정리하세요. `Look`을 지웠을 때 `PlayerAimController`가 `LookInput`을 참조하고 있었습니다.

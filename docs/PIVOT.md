# 기획 전환 — 총에서 메카로

2026-10-25 결정. 전환이 끝나면 이 문서는 지워집니다.

## 이 문서의 수명

여기 적힌 **"전환 후" 구조는 아직 코드에 없습니다.** 결정과 근거를 모아두는 곳이고, 각 단계를 구현할 때마다 해당 내용을 [ARCHITECTURE.md](ARCHITECTURE.md)로 옮기고 여기서 지웁니다. 전부 옮겨지면 이 파일을 삭제합니다.

다른 문서에는 전환 **이력을 남기지 않습니다.** 기존 문서는 항상 "지금 무엇이 맞는가"만 말해야 하고, 과거 기획의 흔적이 섞이면 어느 쪽이 유효한지 읽는 사람이 판단해야 합니다.

## 무엇이 바뀌었나

**총을 든 사람에서 메카 유닛으로.** 플레이어는 조립된 기체를 조종합니다.

**무기는 진입할 때 들고 간 것만 씁니다.** 필드에서 무기를 주워 바꿔 드는 흐름이 사라집니다. 대신 자원·부품·탄약을 파밍해서 들고 나오는 **탈출형 루프**가 됩니다.

이 두 가지가 아래 모든 변경의 뿌리입니다.

## 결정 목록

| 항목 | 결정 |

| 무장 운용 | 좌우 동시 장착. 좌클릭=좌무기, 우클릭=우무기 |

| 탄약 | 유지. 재장전만 없애고 적재함에서 **자동 급탄** |
| 정조준 | 없음. 나중에 자동조준 모듈로 다시 나올 수 있다 |

| 인벤토리 | 필드 파밍 + 탈출형. 적재함이 된다 |
| 핫바 | 폐기 |
| 수리·회복 | 안전지대에서만. 소모품 사용 수단 전부 폐기 |
| 장비 교체 | 안전지대에서만 |
| 회전 | 기체 전체가 한 덩어리로 커서를 향한다 |
| 조립 | 소켓은 프리팹에, 스탯은 SO에. SO가 프리팹을 참조한다 |
| 모딩 | 무기 전용에서 모든 파츠로 일반화 |

## 용어

지금 "파츠"라는 말이 두 층에 겹쳐 쓰이고 있습니다. 층을 나눠 단어를 다르게 줍니다.

| 층 | 용어 | 슬롯 | 데이터 | 프리팹 | 예 |
|---|---|---|---|---|---|
| 기체 조립 | **파츠** | `PartSlotType` | `PartDataSO` | **필수** | 코어, 팔 무기, 추진체 |
| 파츠 모딩 | **모듈** | `ModuleSlotType` | `ModuleDataSO` | 선택 | 스코프, 냉각기, 보조 스러스터 |
| 수치 개량 | **개량** | 없음 | `UpgradeSO` | 없음 | 총열 강화 1~3단계 |

구분 기준은 **"비주얼이 유닛 실루엣을 바꾸는가"**입니다. 파츠는 기체 모양 자체를 만들고, 모듈은 파츠에 얹힙니다.

"파츠마다 모듈이 더 붙는다"가 이 체계의 한 줄 요약입니다.

**리네임** — `WeaponPartDataSO` → `ModuleDataSO`, `WeaponPartSlotType` → `ModuleSlotType`, `WeaponPartBehaviour` → `ModuleBehaviour`, `WeaponModController` → `ModdingController`.

## 슬롯

```csharp
public enum EquipSlotType
{
    None = 0,
    ArmLeft = 1,      // ← PrimaryWeapon
    ArmRight = 2,     // ← SecondaryWeapon
    Core = 6,         // ← Chestplate
    Booster = 12,     // 신규

    // 폐기: 3(Tool) 4(Helmet) 5(Face) 7(Bagpack) 8(HeadPhone) 9(Battery) 10(UtilLoadout)
}
```

**멤버 이름만 바꾸고 값은 그대로 둡니다.** `EquipableItemDataSO._allowedSlots`에 저장된 int가 그대로 맞아떨어집니다. 폐기한 값은 재사용하지 않습니다([RULES.md](RULES.md#식별자)).

적재 칸 수(기존 Bagpack)와 전력(기존 Battery)은 **코어·추진체의 하위 모듈**로 내려갑니다. 슬롯을 늘리지 않고 모딩 층에서 해결합니다.

도구는 팔 슬롯을 씁니다. "한 팔은 드릴, 한 팔은 총" 같은 선택이 생깁니다. **무기 판정과 도구 판정은 캐스터 레벨에서 분리**합니다 — 슬롯을 공유하는 것과 판정을 공유하는 것은 다릅니다.

## 입력

좌우 무장이 동시에 활성이므로, 라우터가 **하나를 골라 넘기는** 구조에서 **슬롯별로 고정 배분하는** 구조가 됩니다.

| 하드포인트 | 공급원 | 입력 |
|---|---|---|
| 좌 무장 | `Equipment[ArmLeft]` | 좌클릭 |
| 우 무장 | `Equipment[ArmRight]` | 우클릭 |

배분표가 `PlayerHandController` 한 파일에만 있다는 원래 의도는 유지됩니다. **`HandActionBase`에 "내가 나설 차례인가" 판단을 넣지 않는 선**만 지키면 됩니다 — 그게 깨지면 조건이 흩어지고 둘 다 반응하거나 아무도 반응하지 않는 상태가 생깁니다.

각 손이 버튼 하나만 받으므로 인터페이스가 합쳐집니다.

```
OnPrimaryPressed / OnSecondaryPressed  →  OnUsePressed / OnUseReleased
```

**정조준이 우클릭 자리를 잃습니다.** 기능 자체를 없애되 `PlayerAimController.SetAiming`과 카메라 줌 기계장치는 **지우지 않고 입력 연결만 끊습니다.** 자동조준 모듈이나 저격형 코어가 재사용할 자리입니다.

## 과열

재장전이 없어진 자리를 과열이 메웁니다.

- 발사마다 열이 오르고 시간이 지나면 식습니다
- 열이 높을수록 공격속도가 **아주 미미하게** 떨어집니다
- 임계를 넘으면 일정 시간 그 무기를 쓸 수 없습니다 (오버히트 락)

**구현은 기존 패턴에 그대로 얹힙니다.** `WeaponStatus`가 origin 기반 modifier와 `RemoveModifiers(origin)`을 갖고 있으므로, 열 컨트롤러가 `AttackCooltime`에 percent modifier를 걸고 식으면 자기 origin으로 걷어냅니다. 파츠가 쓰는 방식과 똑같습니다.

**열 상태는 무기 오브젝트가 들고 갑니다.** `ItemInstance`가 아닙니다. 핫바가 없어져서 무기 오브젝트가 전투 중에 파괴되지 않고, 교체는 안전지대에서만 일어나므로 그때 식는 것이 자연스럽습니다.

**오버히트 락은 `ItemUsability`가 아니라 쿨타임 쪽 표현입니다.** `ItemUsability`는 "손을 쓰지 않으면 영영 안 풀리는 상태"만 봅니다. 락은 기다리면 풀리므로 `_cooldownFill` 자리에 들어갑니다 — 소모품 쿨타임이 쓰던 UI가 그대로 재활용됩니다.

**새 스탯** — `WeaponStatType` 뒤에 `HeatPerShot`, `HeatCapacity`, `HeatCooling`, `OverheatLockTime`을 추가합니다. 소프트 페널티 계수는 전역 상수로 시작하고, 무기마다 달라야 할 때 스탯으로 올립니다.

**`MagazineSize`(7)와 `ReloadTime`(8)은 지울 수 없습니다.** `WeaponStatus`가 배열 인덱스로 쓰므로 자리를 비워두고 폐기 주석만 답니다.

## 탄약

재장전 동작만 사라지고 탄약 개념은 남습니다. 적재함의 탄을 쉬지 않고 당기다가, 다 떨어지면 그 무기는 끝입니다.

**`WeaponAmmoController`는 "탄창"에서 "급탄기"가 됩니다.** `WeaponItemInstance`의 탄창 상태 중 **장전 탄종만 남고 현재 탄 수는 사라집니다** — 적재함 재고가 곧 잔탄입니다.

**탄종은 안전지대 로드아웃에서 지정합니다.** 재장전 홀드로 순환하던 경로가 없어졌기 때문입니다. `CollectAvailableAmmo`가 이미 있으므로 격납고 UI에 그대로 붙습니다. STATUS의 "탄종 전환 UI 미착수"가 여기서 해소됩니다.

**주의** — 발사마다 인벤토리를 조회하게 됩니다. 연사 무기에서 캐시가 필요할 수 있습니다.

## 전력과 연료

`VitalStatus`의 기계장치가 거의 그대로 맞습니다.

| | 전력 | 연료 |
|---|---|---|
| 전신 | 스테미너 | 허기·갈증 |
| 쓰는 것 | 발사, 실드 | 부스터, 이동 |
| 회복 | 시간당 (제너레이터) | **안 됨.** 보급 아이템만 |
| 고갈 | 임계치까지 차야 재사용 | 이동 페널티 + 지속 피해 |

전력의 "바닥나면 일정 비율까지 차야 다시 쓸 수 있다"(`_staminaRecoverThreshold`)는 규칙이 에너지 무기에 정확히 맞습니다. 연료는 허기·갈증에서 **시간당 자동 감소만 제거**하고 소모처를 이동으로 바꿉니다.

`TryConsumeStamina(amount)`는 `TryConsume(VitalType, amount)`로 일반화합니다. "무엇이 쓰는지는 `VitalStatus`가 정하지 않는다"는 원칙은 그대로입니다.

## 조립

코어 스프라이트가 13종이고 실루엣이 제각각이라, 팔이 붙는 위치를 **SO에 숫자로 넣으면 반드시 어긋납니다.** 스프라이트를 바꿀 때마다 숫자를 따로 고쳐야 하기 때문입니다.

**소켓은 프리팹에 Transform으로 둡니다.** 선례가 이미 있습니다 — `PlayerWeaponBase._mountPoints` + `GetMountPoint(slot)`이 무기 파츠 부착을 그렇게 하고 있습니다. 그 구조를 기체 전체로 일반화합니다.

```
PartDataSO (에셋)      Id, 이름, 스탯, 호환 정보 … "무엇인가"
    │ prefab 참조
    ▼
PartView (프리팹)      스프라이트, 소켓, Animator … "어떻게 생겼고 어디에 붙나"
    └ Sockets[] : (PartSlotType, Transform)
```

**SO가 프리팹을 참조합니다.** `PlayerWeaponDataSO.playerWeaponPrefab`과 같은 방향입니다. 인벤토리·격납고 UI가 SO만 보고도 모든 걸 알 수 있어야 하기 때문입니다.

조립은 재귀이고, 규칙은 하나입니다 — **소켓은 호스트가 제공하고, 게스트는 자기 Pivot을 소켓 원점에 맞춘다.**

```
Equipment[Core] 변경
  → 코어 프리팹 생성
  → 코어의 Socket(ArmLeft)에 좌팔 프리팹을 자식으로 생성
  → 좌팔의 Socket(Scope)에 모듈 프리팹 생성
```

**스탯과 비주얼은 끝까지 분리합니다.** 프리팹이 안 꽂힌 파츠도 스탯은 적용되어야 합니다 — 안 그러면 아트가 안 나온 파츠로 밸런스를 볼 수 없습니다. `ModdingController`가 "프리팹 유무와 무관하게 스탯은 한 곳에서"를 이미 그렇게 해두었고, 같은 원칙을 가져갑니다.

적 메카도 같은 조립기를 씁니다. `UnitDataSO`에 파츠 구성을 넣으면 플레이어와 **완전히 같은 경로로** 생성됩니다.

### Pivot은 스프라이트가 아니라 프리팹에서

Root(소켓)는 호스트 쪽, Pivot은 게스트 쪽이라 주인이 다릅니다. Pivot을 어디에 둘지가 갈립니다.

| | 스프라이트 임포터 Pivot | 프리팹 안 offset |
|---|---|---|
| 시트 공유 | 코어 13종이 한 시트라 하나씩 찍어야 함 | 무관 |
| 재임포트 | 설정이 날아갈 위험 | 안전 |
| 툴에서 드래그 | `TextureImporter`를 거쳐야 함 | Transform이라 그냥 핸들 |
| 같은 이미지 재사용 | Pivot 하나만 가능 | 프리팹마다 다르게 가능 |

**프리팹 안 offset을 씁니다.** `PartView` 아래에 `SpriteRenderer`를 자식으로 두고 그 로컬 위치가 곧 Pivot 보정입니다. 스프라이트 에셋은 전부 Center Pivot으로 두고 손대지 않습니다.

### +X가 앞이라는 규칙은 조립에도 걸립니다

기체 전체가 한 덩어리로 커서를 향하므로, **코어 스프라이트도 +X를 앞으로 두고 임포트해야 합니다.** 탑다운 리소스는 보통 위쪽(+Y)을 앞으로 그리므로 그대로 쓰면 기체가 옆을 보고 날아갑니다.

보정은 **`PartView` 루트에서 한 번만** 합니다. 소켓 좌표까지 같이 돌아가야 하기 때문입니다. 소켓마다 따로 돌리면 규칙이 두 개가 되고, [INCIDENTS.md](INCIDENTS.md#총은-왼쪽을-보는데-총알은-오른쪽으로-나간다)와 같은 종류의 사고가 납니다. Part Forge가 생성 시점에 이 보정을 강제합니다.

## Part Forge (에디터 툴)

`Tools > Part Forge`. 파츠 에셋과 프리팹을 한 자리에서 만들고 소켓을 맞춥니다.

**생성** — 파츠 타입 + 스프라이트를 주면:
- `PartDataSO` 에셋 (이름 규칙 + Id 대역 발급 — `ItemCreatorWindow`가 하던 일 재사용)
- `PartView` 프리팹 (SpriteRenderer + 타입별 기본 소켓 세트 + 앞 방향 보정)
- 둘을 서로 연결

**일괄 생성** — 시트 하나에 코어 13종이 들어있으므로, 스프라이트 여러 개를 선택해 한 번에 찍어내고 소켓 기본값을 복사하는 경로가 필요합니다. 손으로 13개를 만들면 시작부터 지칩니다.

**조정** — 코어만 띄워놓고 소켓을 찍으면 팔을 붙여봐야 어긋난 걸 압니다. **조립된 상태로 보면서** 맞춰야 합니다.

```
┌──────────────────────────┬──────────────────────┐
│                          │ 파츠 타입  [Core ▾]    │
│      [ 조립 미리보기 ]      │ 스프라이트 [Unit_Core] │
│   코어 + 테스트 팔/추진체    │                      │
│   ● 소켓 핸들 드래그        │ 소켓                  │
│   ○ Pivot 핸들 드래그       │  ArmLeft  (-0.3, 0.1) │
│                          │  ArmRight ( 0.3, 0.1) │
│   [테스트 파츠 교체 ▾]      │  Booster  ( 0, -0.4)  │
└──────────────────────────┴──────────────────────┘
```

테스트 파츠를 갈아끼우며 "이 코어에 저 팔을 달면 어떻게 보이나"를 즉시 확인합니다.

**검증** — 소켓이 빠졌거나, 앞 방향 보정이 안 됐거나, SO와 프리팹의 연결이 끊어진 파츠를 찾아냅니다.

값은 `SerializedProperty`로 씁니다 — Undo와 dirty 처리가 자동으로 됩니다([CONVENTIONS.md](CONVENTIONS.md#에디터-툴)).

## 애니메이션

조립이 동적이라는 게 함정입니다. **유니티 Animator는 경로 기반 바인딩**이라, 코어에 Animator 하나를 두고 `Socket_ArmLeft/Arm_Rifle/...`을 애니메이트하면 팔을 교체하는 순간 바인딩이 끊깁니다. 파츠 조합이 수십 가지인데 경로가 전부 다릅니다.

| 무엇 | 어디서 | 왜 |
|---|---|---|
| 루프 (부스터 화염, 코어 아이들) | 파츠별 독립 Animator | 조립 구조와 일치해서 교체해도 안 깨진다 |
| 단발 (반동, 피격 움찔, 오버히트 떨림) | DOTween 코드 | 짧고 수가 많다. 에셋이 안 늘어난다 |
| 전신 (피격 리액션) | 코어 Animator가 **소켓만** 흔든다 | 소켓은 어떤 파츠가 붙어도 항상 존재한다 |

전신 연출은 실제로 필요해질 때 붙입니다. 소켓만 애니메이트하는 것이 루트 Animator를 안전하게 쓰는 유일한 방법입니다.

전부 이벤트 구독입니다. 전투 로직이 직접 재생하면 서버 권한 구조로 옮길 수 없습니다([RULES.md](RULES.md#멀티플레이-대비)).

## 아직 안 정한 것

- **코어가 조준점 말고 무엇을 더 정하나** — `AimRange`는 코어로 옮기는 게 맞아 보입니다. 좌우 무기가 서로 다른 `AimRange`를 주장하는 문제가 사라집니다
- **오버히트 락 중에 반대쪽 무기는?** 둘 다 과열되면 무장이 통째로 멈춥니다. 의도한 긴장인지, 코어 모듈로 완화할지
- **탈출 실패 시 적재함 처리** — [MILESTONE.md](MILESTONE.md)의 "죽으면 인벤토리를 어떻게 하나"가 탈출형에서 다시 열립니다
- **파츠 내구도** — 파츠별로 깎이는지, 기체 체력 하나인지
